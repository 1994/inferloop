# 可扩展的图像前处理与设备传输（未完成）

目标是在单图和持续多图服务负载下减少 CPU 解码、patch 生成和主机传输压力，同时保持模型的图像语义、资源上限与取消安全。当前服务仍在 CPU 上完成解码和 patch 生成；CUDA RGB8 前处理、nvJPEG 库探测和 JPEG 头解析仅为测试原型，不能作为已接入的 backend SPI 或 GPU 加速能力。

## 归属与扩展边界

- 输入层负责有界读取、格式识别与必要的头信息解析；读取、头解析和解码前都要为实际可能的暂存分配额度。格式标识和头部尺寸是不可信输入，执行解码时必须再次验证，不得只凭头部声明分配或发布结果。
- 模型 provider 负责 resize 规则、归一化、patch 布局、占位符与 token 几何；请求级图像参数与服务默认值先解析为明确的有效配置。backend 不根据模型名称推断这些语义。
- 在既有 IR 和 backend SPI 上表达编码图像、已准备 patch 及其语义，使 runtime 只协调有界准入、任务和所有权，不依赖具体 CUDA 或 Metal 类型。backend 负责设备能力、格式支持、解码器、物理缓冲和执行；新增格式或 backend 应能提供实现而不改公共调度策略。
- CUDA 的设备属性、驱动版本、平台事实和库候选继续集中在 `crates/backend/cuda/src/device`。硬件和库探测要绑定实际设备；Windows 的 DLL、ABI、依赖及制品仍需单独实现和验证。
- nvJPEG 应根据库、设备及每张图片的实际支持情况区分 hardware、GPU-hybrid 等实现；不要从 GPU 商品名称推断支持。对已实现格式先使用成熟库，库不支持的格式可以由 backend 的独立实现扩展。选择必须受数值合同约束，并用设备属性及加载期测量适配图片尺寸和并发；不引入环境变量作为调优开关。未支持、未通过数值验证或不可用的路径要返回明确错误；任何回退必须是调用方可知、受支持的策略。

## 资源和执行

1. 每项请求在入口保留编码数据及其相关所有权；先报价再分配。报价分别覆盖压缩输入、解码器 host/pinned/device scratch、原始图像、resize 中间结果、patch、视觉塔工作区和需要保留的输出，按实际并发与重用方式计算峰值。
2. 设备相关初始化、解码和预处理由对应 backend 的设备 owner 协调。复用有界解码状态和缓冲；并发数、批量及流的选择要经过测量，不创建每请求线程或无界队列。多图保持输入顺序和 prompt span 对齐。
3. 取消、超时、HTTP 断开或 CPU 返回不表示 GPU 完成。编码输入、pinned 缓冲、解码状态、scratch、设备输出和额度至少保留到对应 device fence 与 CPU reader 完成；不能证明完成时隔离受影响的设备资源。
4. 尽量让解码后的图像、patch 和视觉塔中间结果保持设备驻留，减少反复 H2D/D2H；模型融合位置及完整输出仍须与既有路径一致。资源不足时的等待、拒绝与公平性沿用现有 bounded admission 和 scheduler 合同，不增加绕过配额的路径。

## 验收

- 对每个 decoder/resize 路径覆盖完整像素、patch、grid、顺序、边界、损坏输入及不支持格式；与独立参考比较，不放宽现有容差。JPEG 解码器之间已有可观察差异，必须实际验证并解释，不能假定 nvJPEG 和现有 decoder 位一致。
- 设备测试覆盖成功、取消、资源耗尽、解码失败、fence 失败与释放；无 GPU 的编译、host mock 或全忽略测试不能证明设备支持。
- 在独占硬件窗口对相同模型、图片、resize 参数、输出长度和资源设置，用 release 构建分别测单图与持续多图请求，记录成功率、吞吐、TTFT/TPOT、尾延迟、CPU/GPU 利用率、主机/设备峰值与启动成本，按场景保留慢例及原始样本。decoder 微基准与端到端服务结果分别报告。
- 与 vLLM 对比需要相同模型及输出合同。当前正常 Qwen3-VL 的 DeepStack 尚未实现；禁用 DeepStack 的实验不证明完整模型兼容或可比性能。当前 PR 的无卡 CI、测试原型和主机实验也不能替代设备及服务验收。
